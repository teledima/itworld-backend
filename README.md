# ITWorld-backend тестовое задание

## Инструкция по запуску

### Cервер
`docker compose up server -d`

В результата будет создана:
- База данных postgresql на порту 5432, креды (`user=postgres; password=postgres`)
- Веб сервис на порту 8000

### Запуск тестов
Для удобства запуска тестов, команда была вынесена в compose.yaml. Запустить тесты можно командой

`docker compose up server_tests`

### Описание

### HTTP API
Проект написан на Django и реализует следующие эндпоинты

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/api/v1/invoices/` | Создать счёт |
| `GET` | `/api/v1/invoices/{id}/` | Счёт: детали, список поступлений, остаток к доплате |
| `POST` | `/api/v1/invoices/{id}/cancel/` | Отменить счёт |
| `POST` | `/internal/payments/` | Зафиксировать поступление (эмуляция колбэка от платёжного провайдера) |
| `GET` | `/api/v1/merchants/{id}/balance/` | Баланс мерчанта в разрезе валют |
| `GET` | `/api/v1/merchants/{id}/report/?date_from=&date_to=&group_by=&currency` | Отчет |

- Аутентификация публичных api происходит путем передачи `Project.api_key` в заголовке `X-Api-Key`. Логика аутентификации реализовано `AuthTokenMiddleware` из `middleware.py`.
- Для проверки того, что колбэк приходит из доверенного сервиса добавлен заголовок `X-Signature` в котором платежный провайдер должен передать подпись. На нашей стороне эта подпись проверяется с использованием секрета из переменных окружения.
- Валидация входных данных реализована при помощи декоратора `validate_body`. Для валидации необходимо передать модель `pydantic.BaseModel`. Выбран `pydantic`, так как он имеет широкий набор средств для описания моделей, валидации и сериализации/десереализации данных.
- Бизнес-логика реализуется в слое `services`. Во `views` используется функционал из `services`, обрабатываются исключения и сериализуются данные.


### Management команды

#### set_expire
Устанавливает статус EXPIRED для счетов с expired_at < now

Аргументы:
- `merchant_ids` - список мерчантов для фильтрации. По умолчанию проверка идет по всем мерчантам
- `--dry-run` - запуск без внесения изменений в бд. В результате будет показан список счетов, которые будут переведены в `EXPIRED`

Примеры:
- `python manage.py set_expire` - Проверка по всем счетам и изменение статуса в бд.
- `python manage.py set_expire {1, 2}` - Проверка по счетам мерчантов с идентификаторами (1, 2) и изменение статуса в бд
- `python manage.py set_expire --dry-run` - Проверка по всем счетам и вывод идентификатор счетов, статус которых нужно перевести в `EXPIRED`

#### send_notification
Отправляет уведомления о переходе статуса в терминальное состояние. 

### Анализ производительности
АPI для построения отчета, выполняет два запроса
- первый запрос `report-plan-invoice.txt` получает информацию по счетам (сколько оплачено, сколько всего, выставленная сумма)
- второй запрос `report-plan-ledger.txt` на основе ledger получает информацию по текущей оплате (сколько оплачено, сколько взято комиссии)

Так как структурно они похожи, разберем `report-plan-ledger.txt`. 

1. Для получения данных о курсе валют используется индекс exchangerate_base_target_currency_key. Так как он содержит все необходимые данные (`base_currency`, `target_currency`, `amount`) то не посредственно из таблицы бд ничего не читает `Index Only Scan using exchangerate_base_target_currency_key`. `Subplan` означает, что расчет происходит в подзапросе.
2. Таблица `payments_ledger`. Сначала используется индекс по `merchant_id` и создается битмап (`Bitmap Index Scan on payments_ledger_merchant_id_78ef0b75`). Далее вычитывается таблица `payments_ledger` по условию на столбец `dt` и на основе битмапа из предыдущего шага. Битмап здесь используется, так как только по индексу бд не может проверить все фильтры и необходимо дополнительно обращаться к самой таблице.
3. Для таблицы `payments_invoice` для выполняется только `Index Scan` (находятся номера строк по индексу и затем бд извлекает отфильтрованные строки из таблицы).
4. Выполняется джойн `Nested Loop Left Join`
5. Выполняется группировка и агрегация GroupAggregate

### Допущения
- Информация о мерчанте выводится по переданному id, хотя с точки зрения разграничения прав это не совсем корректно, так как апи ключ привязан к проекту. Корректная реализация включает себя создание апи ключей на уровне мерчанта. Если предполагается, что несколько мерчантов могут принадлежать одному владельцу, то тогда должна быть создана сущность, которая это будет отражать, например merchants_groups. И соответсвенно управление апи ключа должно быть перенесено туда.
- Предолагается, что пользователь может отменить счет или время может истечь. Здесь стоит рассмотреть кейс, когда счет уже частично погасили и пользователь или система хочет его закрыть(перевести в CANCELLED/EXPIRED). Как в этом случае поступать с уже внесенными средствами? Я предполагаю что оптимальным будет выполнить возврат средств. Для реализации этого нужно в момент получения платежа в /internal/payments или в момент отмены счета пользователем создать запись на возврат и фоновой джобой отправлять запросы на возврат в сервис платежей. Так же стоит учитывать, что возврат по api по каким-то причинам будет невозможно провести и необходимо связываться с клиентом и обсуждать другие варианты возврата.
- Предполагается, что на момент построения отчета по валюте, все требуемы курсы валют есть в системе. Как минимум я бы добавил логирование случаев, когда требуемой конвертации нет в системе с приоритетным исправлением пайплайна по получению курсов обмена.
- для построения отчета добавлен параметр currency - курс в котором будет считаться отчет. Без этого параметра непонятно, как считать агрегации по деньгам, т.к. у мерчанта могут быть счета и пополнения в разных валютах.
- При отправке нотификации не вижу возможности добится 100% гарантии, что она не отправится дважды. Здесь все упирается в сетевое взаимодействие, которое заведомо является нестабильным и это не всегда можно корректно отловить. Поэтому вводится idempotency-key для того чтобы на стороне клиента можно было обработать сообщение только один раз
- Минимальная сумма счета задана в 10 у.е. т.к. при меньших значениях коммисия будет съедать большую часть суммы. Например, если открыть счет на 1 у.е., то комиссия будет 0.5 у.е.
